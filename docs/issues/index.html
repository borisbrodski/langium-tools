Document issues

A Langium document keeps syntax failures on parseResult and semantic diagnostics on diagnostics. Callers that read only one of those miss the other. This module returns a single list, with a source, a severity, a message, and a position.

Read every issue

getDocumentIssues walks lexer errors, parser errors, and validation diagnostics. Each item is a DocumentIssue.

issues.ts 
import { getDocumentIssues } from 'langium-tools/base';

const issues = getDocumentIssues(document);

What goes into the list

  • LEXER — tokenization failures. Always an error. Offset, line, and column come from the lexer and are stored 0-based.
  • PARSER — syntax errors. Always an error. The position is the token that failed, or the previous token when Chevrotain reports an inserted EOF at -1.
  • VALIDATION — diagnostics from your validators. Severity follows the language server: error, warning, information, hint.

Printed strings from documentIssueToString are 1-based (Error at 4:13-20). The fields on the object stay 0-based, which matches LSP ranges and the marker parser.

Skip what you do not care about

A generator often wants to stop on syntax errors and ignore hints. A test for a warning wants the opposite. The second argument filters the list. Every flag defaults to false, so the default call returns everything.

errors-only.ts 
const errorsOnly = getDocumentIssues(document, {
  skipNonErrorDiagnostics: true, // drop warnings, information, hints
  skipLexerErrors: false,
  skipParserErrors: false,
  skipValidation: false,
});

A summary you can log

getDocumentIssueSummary counts errors and everything else, builds a one-line summary, and builds a message grouped by source. summary.countErrors is the number to branch on in a CLI. Headings are Lexer errors, Parser errors, and Diagnostics. Validation is not called “validation issues” in the one-line summary: errors become error diagnostic(s) and the rest become non-error diagnostic(s). getDocumentIssueSummaryFromIssues is the same summary for a list you already have.

summary.ts 
import { getDocumentIssueSummary } from 'langium-tools/base';

const summary = getDocumentIssueSummary(document);
console.log(summary.countErrors); // every ERROR, including lexer and parser
console.log(summary.summary);
// "1 lexer error(s), 1 parser error(s), 1 error diagnostic(s), 2 non-error diagnostic(s)"
console.log(summary.message);

summary.message looks like this:

stdout 
Lexer errors:
Error at 2:5 - Invalid character.
Parser errors:
Error - Unexpected token.
Diagnostics:
Warning at 5:1 - Unused import.
Hint at 6:10 - Consider renaming variable for clarity.
Error at 8:15 - Type mismatch.

1 lexer error(s), 1 parser error(s), 1 error diagnostic(s), 2 non-error diagnostic(s)

One issue, one line

print.ts 
import { documentIssueToString } from 'langium-tools/base';

for (const issue of issues) {
  console.log(documentIssueToString(issue));
}
// Error at 3:15 - unexpected character
// Warning at 5:10-18 - Deprecated.

Parser end positions are left unset on purpose. Chevrotain's recovered end offset is not reliable enough to draw a span. Validation issues do carry an end line and end column, taken from the diagnostic range.

The enums

  • DocumentIssueSource — LEXER, PARSER, VALIDATION.
  • DocumentIssueSeverity — ERROR, WARNING, INFORMATION, HINT, UNKNOWN.

severityToString maps a language-server DiagnosticSeverity to Error, Warning, Information, or Hint. A printed issue uses the enum value instead: INFORMATION is stored as INFO and prints as Info. A parser issue with no usable position prints as Error - … with no at clause. The end column on one line is the 1-based column after the span, so 4:13-20 covers columns 13 through 20.
