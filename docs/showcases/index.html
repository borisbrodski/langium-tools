Showcases

Each directory in langium-tools-showcases is one language. The projects do not share a package.json or a build. Add the next language as another directory and point it at the same sibling checkout of langium-tools.

State machine

The official Langium state-machine example. Same grammar, same C++ program, plus issues, an in-memory generator, a Java event file, and snapshot tests.

Clone it next to the library

The state machine depends on file:../../langium-tools. This package publishes dist/, so build the library before npm install in the showcase. Node must be ^22.22.2, ^24.15.0, or >=26.

directories 
langium-tools/
langium-tools-showcases/
  statemachine/
terminal 
git clone https://github.com/borisbrodski/langium-tools.git
git clone https://github.com/borisbrodski/langium-tools-showcases.git
cd langium-tools && npm install && npm run build
cd ../langium-tools-showcases/statemachine
npm install
npm test

npm test builds the language and compares generated/ with GENERATOR_TEST=verify. npm run test:generate rewrites those snapshots.

State machine

statemachine is the official Langium state-machine example. The grammar and the C++ program stay that example. langium-tools is the CLI report, the file collector, the Java event file, and the tests around them. Branch upstream is the official copy. main is the extension. The diff is the lesson.

langium-tools-showcases 
git diff upstream -- statemachine

Issues in the CLI

getDocumentIssueSummary is the only error report. Lexer, parser, and validation errors share one count. Warnings are printed and generation continues. Errors stop the command.

Markers in the tests

toHaveNoErrors ignores warnings. toHaveNoIssues includes them. A lowercase state name is the sample that shows the difference, so a style warning does not fail a parse test. parseWithMarks and toHaveDocumentIssues use <<{| … |}>> as the expected range. The markers are stripped before Langium sees the text.

Generate, then write

generate only calls createFile. The CLI calls writeToDisk. Identical bytes keep their modification time. The same path with different text throws before a file is overwritten. The C++ templates themselves are unchanged. A Java file for the events is a second artifact of the same model. Pass workspace directories as URI.file. A raw filesystem string goes through URI.parse and is not a file URI.

Snapshot tests

langiumGeneratorSuite builds each workspace under test/generator/, generates in memory, and compares content and the overwrite flag to generated/ and generated-metadata.json. createServices returns the official { shared, statemachine } pair, which is the one non-shared service the suite requires.

Java events

JavaImportManager and packageToPath build com/example/TrafficLightEvents.java. useClass runs before generateImports. The current package is not imported. A second type with the same simple name stays fully qualified. The file is written with createFile. An empty event list cannot be a Java enum, so that model emits a final class with a private constructor.

generator.ts 
const imports = new JavaImportManager('com.example');
const consumer = imports.useClass('java.util.function.Consumer');
// consumer === 'Consumer'
// imports.generateImports() === 'import java.util.function.Consumer;'

generateJavaFile is the one-call wrapper in the Java guide. It builds the file with generator nodes from the Langium install inside langium-tools. A project that also depends on Langium has a second copy, and those nodes print as [object Object]. The showcase calls JavaImportManager and createFile. The note is in statemachine/src/cli/generator.ts.

Left for a language that needs them

arraySortBy would reorder events, and declaration order is the language order. adjustedUnix is for templates whose newlines must be \n on every platform. The snapshots here already are. toFirstUpper and toFirstLower are unused because the names already fit the output. The .cpp and .java files share one output directory, so there is no named generator target. A named target is the next step when those files must land in different directories. Once any custom target is passed to the suite, every target, including the default, is written under generated/<name>/.
